# Production & Costing — Product BOMs

Open **Production & Costing** in the existing shared Product Editor or Product Override Editor. Search the existing Operations inventory by name, permanent ID, supplier SKU or barcode. A line describes the amount needed for **one sellable unit**, not a purchase pack or a production batch. Units must be compatible with the inventory record. Separate lines for the same item are allowed for distinct requirements and are summed; remove any accidental extra line.

## Inheritance and identity

Start with the shared BOM. For example, add one box and one sleeve. In a Product Override, add a printed insert and change the sleeve quantity to two. Only the new insert and the changed sleeve quantity are stored in that override: the box remains inherited. If the shared editor later adds a thank-you card, this product inherits it too.

**Exclude inherited line** is an explicit instruction attached to that shared line. **Reset to inherited** removes just that instruction or modification. **Remove line** on a locally added requirement deletes the addition. If a shared line is deleted rather than edited, conflicting overrides surface for review; they are not applied to a replacement line. Inventory renames and barcode changes do not change references.

## Option Materials & Components

Keep the common requirements in **Main Product BOM**. Under **Option Materials & Components**, expand an actual Shopify variant option value to define its recipe once for every matching variant. These are catalogue options, not customer personalisation or customisation fields.

- **Inherit / No changes** is the default. A value with no rule contributes no instructions. In Product Override, **Use shared rule** follows the shared option rule; explicitly choosing **Inherit / No changes** skips that rule for this product without touching the shared definition.
- **Add to BOM** keeps the inherited recipe and applies only the selected changes. You can add a separate requirement, change the quantity or substitute the item on a particular inherited line, or explicitly exclude that line. Adding to a shared option rule keeps its existing contributions. Resetting a line removes only that adjustment.
- **Replace entire BOM** requires confirmation and an independent complete recipe. Check the inherited and replacement previews; packaging and other inherited lines will not automatically remain. An empty replacement is not zero cost. Changing modes never deletes the main or shared recipe or a variant's manual cost.

**Dumpling example.** Put one body (£0.30), one clicker (£0.15) and one package (£0.20) in the main BOM. Set **Keyring = Yes** to add an attachment (£0.10) and **Lid = Yes** to add a lid (£0.12). Leave both **No** values at Inherit. The four estimated costs are £0.65 standard, £0.75 keyring, £0.77 lid, and £0.87 for both. TLC uses actual inventory cost records, not these illustrative values.

**Print example.** Put A4 paper (£0.11) and protective packaging (£0.20) in the main BOM. Leave **Size = A4** at Inherit. Set **Size = A3** to Add, select the inherited paper line, and substitute A3 paper (£0.23) on that line. A4 costs £0.31 and A3 costs £0.43; both retain packaging. A new style with an A3 variant inherits this same substitution after the normal rescan.

## Individual variants and conflicts

**Individual Variant Adjustments** shows saved exceptions and variants needing attention. Search for any other variant by retained SKU, option values or local variant identity. The order is: shared main recipe → Product Override adjustments → applicable option values → individual variant. An individual variant can Inherit, Add/substitute/exclude specific lines, or deliberately Replace the recipe for that SKU only. Its **Cost source** remains separate. Existing M2 variant overrides without a mode are still additive.

Independent options add their requirements together, even if two separate lines intentionally use the same item. Identical instructions targeting the same inherited line apply once. Incompatible instructions on the same line are reported, not resolved by option order. With exactly one matching option replacement, its independent recipe becomes the base; other option additions still apply. Other targeted instructions must reference a valid line in that base. Multiple matching replacements are a conflict. A variant's deliberate Replace wins for that SKU; a variant Add can resolve a line-specific conflict only by explicitly settling that target. Unrelated edits do not clear it.

Rules use exact saved option names and values, not display positions, and survive reorder. TLC doesn't have a separate stable ID for a renamed option value: if a name/value disappears, the rule is retained and flagged; it never guesses a replacement. After changing the option definitions, save and reopen the editor to configure the new values. Individual exceptions still follow the retained SKU. If a rebuild allocates a new SKU, review the old override rather than assigning it to the new variant by position.

The existing authoritative JSON files hold `production.lines`, `production.cost`, `production.options[option name][value]` and `production.variants[SKU]`. Option and variant rules store a mode where explicitly set. Lines are keyed by stable IDs, using sparse `add`, `modify` and `remove` actions in Add mode; a replacement has only its own independent lines. Inventory item IDs refer to existing SQLite records. No migration rewrites M2 JSON. `app.inventory.product_bom.product_costs()` returns the canonical requirements, source attribution, inventory type, conflicts and estimate per sellable SKU for future picking or assembly. It does not reserve, consume or allocate stock.

## Costs and publication

- **Calculated from BOM** uses M1's decimal-safe costing basis: weighted unreversed costed receipts/opening stock (or the pack price if there are none). Manufactured components use their costed output/opening stock, falling back to the configured recipe estimate until recorded cost is available. A manufactured component contributes its cost once; its raw materials are not automatically added to the finished-product BOM. Editing a fallback pack price or recording a new receipt changes the estimate where the current basis uses it. Old receipts and batch costs are not rewritten.
- **Manual cost** changes the effective cost without deleting the BOM or hiding its estimate. It can override an incomplete estimate under existing M2 publishing rules, but an invalid recipe still shows Needs Attention and isn't ready for picking. Enter `0.00` explicitly if zero is intended. An empty or invalid BOM does not imply a zero cost.
- **Not configured** leaves Shopify's existing value alone. Variants inherit the preceding cost mode unless explicitly configured. Neither postage, fees, labour nor overhead is included unless it is represented by an actual measurable BOM requirement. No VAT is added. Only the final Shopify amount is rounded to GBP pennies, half-up.

The existing **Review & Sync** shows before/after Cost per item per retained variant SKU and indicates whether the pending amount is calculated or manual. Incomplete **managed** costs block the signed plan rather than publishing guessed values. A matching value causes no cost write. The existing Shopify Admin API uses `inventoryItemUpdate` with only `input.cost` on a retained InventoryItem GID, and independently reads `ProductVariant.inventoryItem.unitCost` to verify it in GBP. This requires a GBP shop, `write_inventory` for writes, product or inventory read access and Shopify's **View product costs** permission where applicable; the checked-in app already requests the inventory scopes. Review shows missing permissions or verification failures without changing app configuration. Read-only reconciliation is required after a potentially successful but uncertain mutation.

The existing automatic publisher uses the same cost stage when enabled. A normal scoped scan first establishes the authored BOM revision. The hourly run checks calculated BOMs in rotating batches (up to 24 per run) so cost-only changes can queue updates without a new catalogue scan. It does not adopt unscanned JSON or unrelated changes, publish Drafts automatically or replay an uncertain operation. Shopify receives no BOMs, component records, notes, inventory quantities or location details. Selling prices, Shopify stock tracking and product availability are not changed by the cost stage.

## Manual deployment and acceptance

Back up the existing appdata and catalogue JSON first. Install the verified immutable image without changing the `/app/instance` or source catalogue mounts. M2.1 adds no database migration or new mount on top of M2. No stock or catalogue tables are rebuilt.

On a disposable instance, try the dumpling additions or A3 paper substitution on desktop and phone. Compare sibling variants in **Cost Summary**, find one by SKU, and try an exception. Cancel a replacement to check it leaves the recipe untouched. Save, reopen and check both inherited and exceptional costs. Open **Review & Sync** and verify only matching variants have changed costs. For a controlled Shopify acceptance, approve one change on a non-production product/shop, compare Cost per item on the exact variant, and check for verified readback. Confirm the selling price and stock settings did not change.
