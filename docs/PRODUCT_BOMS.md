# Production & Costing — Product BOMs

Open **Production & Costing** in the existing shared Product Editor or Product Override Editor. Search the existing Operations inventory by name, permanent ID, supplier SKU or barcode. A line describes the amount needed for **one sellable unit**, not a purchase pack or a production batch. Units must be compatible with the inventory record. Separate lines for the same item are allowed for distinct requirements and are summed; remove any accidental extra line.

## Inheritance and identity

Start with the shared BOM. For example, add one box and one sleeve. In a Product Override, add a printed insert and change the sleeve quantity to two. Only the new insert and the changed sleeve quantity are stored in that override: the box remains inherited. If the shared editor later adds a thank-you card, this product inherits it too.

**Exclude inherited line** is an explicit instruction attached to that shared line. **Reset to inherited** removes just that instruction or modification. **Remove line** on a locally added requirement deletes the addition. If a shared line is deleted rather than edited, conflicting overrides surface for review; they are not applied to a replacement line. Inventory renames and barcode changes do not change references.

For a variable product, expand its variant row. The variant starts with the resolved parent BOM, then applies any shared definitions targeted at its exact retained SKU and then any variant changes from the product override. For example, A4 can inherit the sleeve and insert while adding A4 paper; A3 can add different paper and exclude the sleeve. Renaming a display label or changing order does not change the key. If a catalogue rebuild genuinely allocates a different SKU, do not assume it is the old variant: inspect and re-enter any intended recipe under the new identity. Unmatched product override recipes are retained and flagged, not silently reassigned.

The existing authoritative JSON files hold `production.lines`, `production.cost` and `production.variants`. Lines are keyed by stable line IDs, using sparse `add`, `modify` and `remove` actions. Inventory item IDs refer to existing SQLite records. There is no new inventory ledger or product authority. `app.inventory.product_bom.product_costs()` provides the resolved requirements, inventory type and estimate by sellable SKU for future picking or assembly; it does not reserve, consume or allocate stock.

## Costs and publication

- **Calculated from BOM** uses M1's decimal-safe costing basis: weighted unreversed costed receipts/opening stock (or the pack price if there are none). Manufactured components use their costed output/opening stock, falling back to the configured recipe estimate until recorded cost is available. A manufactured component contributes its cost once; its raw materials are not automatically added to the finished-product BOM. Editing a fallback pack price or recording a new receipt changes the estimate where the current basis uses it. Old receipts and batch costs are not rewritten.
- **Manual cost** changes the effective cost without deleting the BOM or hiding its estimate. It can override an incomplete estimate. Enter `0.00` explicitly if zero is intended. An empty or invalid BOM does not imply a zero cost.
- **Not configured** leaves Shopify's existing value alone. Variants inherit the preceding cost mode unless explicitly configured. Neither postage, fees, labour nor overhead is included unless it is represented by an actual measurable BOM requirement. No VAT is added. Only the final Shopify amount is rounded to GBP pennies, half-up.

The existing **Review & Sync** shows before/after Cost per item per retained variant SKU and indicates whether the pending amount is calculated or manual. Incomplete **managed** costs block the signed plan rather than publishing guessed values. A matching value causes no cost write. The existing Shopify Admin API uses `inventoryItemUpdate` with only `input.cost` on a retained InventoryItem GID, and independently reads `ProductVariant.inventoryItem.unitCost` to verify it in GBP. This requires a GBP shop, `write_inventory` for writes, product or inventory read access and Shopify's **View product costs** permission where applicable; the checked-in app already requests the inventory scopes. Review shows missing permissions or verification failures without changing app configuration. Read-only reconciliation is required after a potentially successful but uncertain mutation.

The existing automatic publisher uses the same cost stage when enabled. A normal scoped scan first establishes the authored BOM revision. The hourly run checks calculated BOMs in rotating batches (up to 24 per run) so cost-only changes can queue updates without a new catalogue scan. It does not adopt unscanned JSON or unrelated changes, publish Drafts automatically or replay an uncertain operation. Shopify receives no BOMs, component records, notes, inventory quantities or location details. Selling prices, Shopify stock tracking and product availability are not changed by the cost stage.

## Manual deployment and acceptance

Back up the existing appdata and catalogue JSON first. Install the verified immutable image without changing the `/app/instance` or source catalogue mounts. The additive startup migration only adds derived cost-check fields to the existing publishing work records. No stock or catalogue tables are rebuilt.

On a disposable instance, give a sample component a known price; add it to a shared product; add a different line in one product override; then add or exclude a line in one variant. Reopen the editors and check other variants still inherit. Set and reset a manual cost, then open Review & Sync without confirming to check each variant's intended amount. For a controlled Shopify acceptance, use a non-production product/shop and approve one cost change. In Shopify Admin, compare Cost per item on the exact variant and return to TLCDashboard to verify matching readback. Confirm the selling price and stock settings did not change.
